# cp-docs 改造前后对比（v0.1.0 → v0.2.0）

> 一句话：**v0.1.0 先猜意图、只取一小片资料，猜错就由模型回答“文档未收录”；v0.2.0 命中机型后直接整包返回该机型全部资料，由模型自行定位。**
>
> 原始报文留档：`docs/baseline/v0.1.0-*.txt`（改造前）、`docs/after/v0.2.0-*.txt`（改造后），均为本机实测。

---

## 1. 两条链路

### v0.1.0（旧）：意图猜测 + 选择性取数

```
/cp-docs <问题>
 → parse.js        切机型串 → 唯一命中
 → query.js:107    detectIntent() 判意图 field / pin / harness / node / workpoint
                     PIN_RE = /(?:pin|第|p)\s*#?\s*(\d{1,2})\s*(?:脚|针|号|位)?/i
 → query.js        field  → 只取参数字段（matchFields）
                   pin    → pickPin(row[0]) 或 pickRows 打分，limit=12
                   node   → 只扫编程节点页
                   workpoint → 只扫工作点列
 → framing.js:16   拼「参数/表格定义/编程节点/工作点 + 出处 + RULE」
                     RULE：未列出的字段 → 直接回答“文档未收录”
 → followup → 模型作答
```

旧结构的三处硬伤：**先猜意图**（猜错就没有表）、**只取一片**（`slice(0,12)`）、**RULE 把“没检索到”写成“未收录”**。

### v0.2.0（新）：整包返回

```
/cp-docs <问题>
 → parse.js        切机型串 → 唯一命中（机型归一逻辑完全未改）
 → store.js        loadModelFiles(): spec.json + programming.json + workpoints.json
                   loadLabels(): fields.json → { key: {label, unit} }
 → packet.js       renderPacket(): 参数/全部表格/编程节点/工作点/未转写图片/数据提示
 → packet.js       buildPacketMessage(): 顶部“用户问题” + 整包 + 作答约束
 → followup → 模型自行定位作答
```

`detectIntent` / `pickRows` / `pickPin` / `matchFields` / `buildFraming` 全部下线；`lib/query.js` 已删除（旧实现见 git tag `v0.1.0`）。

## 2. 同一问题：前后逐条对照

| 问题 | v0.1.0 报文 | v0.1.0 命中内容 | v0.1.0 结论 | v0.2.0 报文 | v0.2.0 结论 |
|---|---|---|---|---|---|
| SPRING2PRO 的RS232的引脚在哪个位置 | 720 字符 | 仅「参数：」= `RS232*2` | 只能答“引脚位置文档未收录”（**漏检**） | 11,574 字符 | 26PIN 表在包内：PIN 14 `RS232_A_TX`、20 `RS232_A_RX`、17 `RS232_B_RX`、24 `RS232_B_TX` |
| SPRING2PRO 26PIN 第24脚是什么 | 2,047 字符 | 「表格定义：」7 行 | 命中表但**不含** `RS232_B_TX`（`pickPin` 只比首列 + 12 行截断） | 11,568 字符 | 直接读到 `24 \| RS232_B_TX/OUTPUT4/PHY_MDI_3+` |
| SPRING2PRO 的屏幕尺寸是多少 | 762 字符 | 参数字段 | 正确（10.1 / 1024\*600） | 11,568 字符 | 正确，且可交叉核对参数表 |
| SPRING2 屏幕尺寸 | —（未触发模型） | 列候选 | 正确 | —（未触发模型） | 不变 |
| CP023 的 INPUT1 接到哪个 GPIO | 629 字符 | 「硬件工作点」 | 按字段合并 1.23/1.25 作答（`[MCU] PC0`） | —（未触发模型） | **行为变化**：两机型整包不同 → 列候选让用户选（见 §4） |
| 支持哪些机型 | 681 字符 | 目录 | 28 款 | 681 字符 | 不变 |

引脚类问题的关键差异：旧包 720 字符里**没有表格**，新包 11.5k 字符里 26PIN 表 26 行一行不少。

## 3. 缺陷映射：为什么 D1–D4 在新结构下消失

| 缺陷（审查编号） | 旧代码 | 消失原因 |
|---|---|---|
| D1 意图分类缺口：`引脚在哪个位置` 判成 `field` | `lib/query.js:107` `detectIntent` | 不再有意图层，所有资料一律返回 |
| D2 `field` 分支不跨表兜底 | `lib/query.js:145-160` | 不存在“分支”，表格固定全量输出 |
| D3 `pickPin` 只比 `row[0]`，4 列并排表 PIN 14–26 永远取不到 | `lib/query.js:53` | 不再挑行，整张表原样输出 |
| D4 `slice(0,12)` 截断 + 同分 | `lib/query.js:40` / `lib/framing.js:28` | 表格行不截断（`renderPacket` 只在 >40000 字符时降级编程节点/工作点） |
| D5 RULE 把“没检索到”等同“未收录” | `lib/framing.js:4` | 报文是整包，未收录=整包确无；约束措辞改为「资料中确实没有的项」 |

## 4. 代价与行为变化（需要 reviewer 确认）

1. **报文变大**：28 机型实测 5,074（1.18）～17,408（1.15）字符，均值 9,220；同一问题从 720 / 2,047 字符涨到约 11.5k 字符，约 **5–25 倍**。换来的是一律不再漏检。
2. **CP 编码跨机型不再合并**：`CP023` 同时对应 1.23 / 1.25，旧版按字段值相同合并作答，新版整包必然不同，改为列候选（更保守，但需要用户写精确机型）。同值合并逻辑现在只在“整包完全一致”时触发（如 1.23 / 1.24 共享资料的情形）。
3. **命令返回文案变化**（可审计，用于确认走的是整包路径）：
   `已命中 1.23 SPRING 10 PRO 二代：全量资料 5 张表 / 33 项参数 / 2 页编程节点 / 4 组工作点，正在生成回答…`
4. **报文头变化**：`【cp-docs 检索结果 · …】` → `【cp-docs 机型资料 · 请只依据以下资料回答】`。
5. **未发送 `doc.md`**：它是 spec 的派生渲染，重复度高且不含编程节点/工作点；原文件仍保留在数据目录。

## 7. v0.2.1：资料不再刷屏（对话框呈现）

v0.2.0 把整包资料作为 `source.kind = 'user'` 的消息 followup，对话框里整段展开（11.5k 字符）。v0.2.1 只改消息来源：

```js
// 旧
source: { kind: 'user' }
// 新
source: { kind: 'cp-docs', form: 'notice', summary: '1.23 SPRING 10 PRO 二代 · 5 张表 / 33 项参数 / 2 页编程节点 / 4 组工作点' }
```

- 正文（`content`）一字未改，模型收到的东西完全一样。
- DSH Web 的 `dsh-client-ui-chat` 在 `client.js:9857` 用 `source.kind !== 'user'` 判定“非用户消息”，唤醒新一轮的这类消息渲染为 `turn-trigger` 节点：默认折叠的一行卡片（`client.js:7108`，`useState(false)`），点开才显示正文（240px 滚动区）。
- 未收录的 kind 使用内置标题文案「收到执行请求」，展开说明「这条通知触发了本轮回复。」（`client.js:5764`）。标题是客户端内置映射，服务端插件无法定制。

实测载荷（同一问题）：`content` 11,574 字符（含 26PIN 表、PIN 24），`summary` 56 字符；`role` 仍为 `user`，`source.kind` 由 `user` 变为 `cp-docs`。
